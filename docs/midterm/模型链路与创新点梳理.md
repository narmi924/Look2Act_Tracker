这份文档的目标不是“看懂代码”，而是让你在答辩时能把下面几件事讲清楚：

1. 当前模型到底是什么
2. 它为什么这样设计
3. 它的输入、输出、参数量和训练方式是什么
4. 它在整个系统链路里起什么作用
5. 你的工作到底有没有创新点，创新点在哪里

---

## 一句话总览

**当前主模型是 `GazeNetV2`：一个“双眼共享 CNN 特征提取 + head pose 融合 + 3D 视线方向回归”的轻量模型。**

它不是“提出全新深度学习范式”的那种创新，而是一个**面向普通 RGB 摄像头桌面场景的结构化改进模型**，并且和几何映射、头姿估计、校准模块一起组成了完整系统。

## 1. 先回答一个关键问题：我的算法到底有没有创新点？

### 简短回答

**有，但更准确地说，是“场景导向的结构创新 + 系统创新”，不是“提出一个全新的基础网络范式”。**

### 更完整的答辩表述

如果老师问“你的算法有没有创新点”，你可以这样回答：

> 严格来说，我的工作不是发明一个全新的深度学习大模型范式，而是围绕“普通 RGB 摄像头桌面视线追踪”这个具体问题，对模型结构、系统链路和实验验证做了面向场景的改进与整合。  
> 当前的创新主要体现在三点：  
> 第一，我没有只做单眼图像回归，而是设计了双眼共享 CNN 与 head pose 融合的 `GazeNetV2`；  
> 第二，我没有把模型停留在离线角度误差上，而是把 3D 视线方向、头姿、屏幕几何映射和用户校准整合成完整系统；  
> 第三，我做了跨用户验证、head pose 消融和校准策略对比，使这条路线不只是“能训练”，而是“被系统性验证过”。  

### 你这项工作的创新点可以拆成 4 层

#### 1. 问题定义层

- 聚焦**普通 RGB 摄像头**
- 聚焦**普通 Windows 桌面环境**
- 聚焦**实时、低成本、可部署**

这和很多只做离线视线估计、或者依赖专用硬件的工作不同。

#### 2. 模型结构层

- 从单眼 CNN 迭代到**双眼共享 backbone**
- 将 **head pose** 作为额外输入显式融合
- 输出不是二维屏幕坐标，而是**三维单位视线方向向量**

这使模型更贴合后续几何映射和跨设备泛化需求。

#### 3. 系统链路层

- CNN 不是单独存在的
- 它和人脸检测、PnP 头姿估计、射线-平面求交、屏幕映射、仿射校准一起构成完整链路

也就是说，你的成果不是“一个模型”，而是“一个可演示的系统”。

#### 4. 实验验证层

- 不是只报测试集精度
- 还做了跨用户 Leave-One-User-Out 验证
- 做了 head pose 消融
- 做了校准策略对比

这部分很重要，因为它说明你的设计不是拍脑袋，而是被实验支持的。

## 2. 当前系统里的模型处在什么位置？

你要把“模型”放到整个系统里理解，而不是单独理解。

### 整体链路

```text
摄像头画面
  ↓
人脸关键点检测（MediaPipe Face Mesh）
  ↓
眼区裁剪（左眼 / 右眼）
  ↓
头部姿态估计（PnP -> yaw / pitch / roll + R + t）
  ↓
GazeNetV2
  输入：left_eye + right_eye + head_pose
  输出：3D gaze unit vector = (gx, gy, gz)
  ↓
坐标系转换
  ↓
射线-平面求交（与屏幕平面相交）
  ↓
屏幕像素坐标 (x, y)
  ↓
平滑处理 + 校准补偿
  ↓
实时注视点输出
```

### 重点理解

`GazeNetV2` 的职责不是直接输出屏幕坐标。  
它的职责是：**从眼部图像和头姿里估计用户当前的三维视线方向。**

后面的屏幕坐标，是几何模块和校准模块继续算出来的。

## 3. 为什么模型输出三维视线方向，而不是二维坐标？

这是答辩时很容易被问到的点。

### 原因 1：问题本质上是 3D 的

用户的眼睛看向某个方向，本质上是一个空间方向问题，而不是天然的二维问题。

### 原因 2：二维坐标耦合了太多设备因素

如果直接回归屏幕二维坐标，模型会把这些东西混在一起学：

- 眼部外观
- 头部姿态
- 摄像头位置
- 屏幕尺寸
- 用户距离

这样泛化通常更差。

### 原因 3：三维输出更方便和几何模型结合

你当前系统后面还有：

- 头姿旋转矩阵
- 平移向量
- 屏幕平面
- 射线-平面求交

所以输出三维视线方向，是更符合你整个系统设计的。

## 4. 当前模型输入输出是什么？

### 输入

- 单眼图像：`(B, 3, 128, 128)`

### 输出

- 三维单位视线向量：`(B, 3)`

---

## V2: `GazeNetV2`

### 输入

- 左眼图像：`(B, 3, 128, 128)`
- 右眼图像：`(B, 3, 128, 128)`
- 头部姿态：`(B, 3)`，对应 `yaw / pitch / roll`

### 输出

- 三维单位视线向量：`(B, 3)`

### 注意

输出最后做了 **L2 归一化**，所以是单位向量。

这意味着模型学的不是“长度”，而是“方向”。

## 5. 当前模型结构长什么样？

## 5.1 V1：GazeNet（单眼基线）

### 结构图

```text
输入：单眼图像 (3, 128, 128)
  ↓
Conv(3→32, 3x3) + BN + ReLU + MaxPool
  输出：(32, 64, 64)
  ↓
Conv(32→64, 3x3) + BN + ReLU + MaxPool
  输出：(64, 32, 32)
  ↓
Conv(64→128, 3x3) + BN + ReLU + MaxPool
  输出：(128, 16, 16)
  ↓
Conv(128→256, 3x3) + BN + ReLU + MaxPool
  输出：(256, 8, 8)
  ↓
AdaptiveAvgPool2d(1)
  输出：(256, 1, 1)
  ↓
Flatten
  输出：256 维
  ↓
FC(256→3)
  ↓
L2 Normalize
  ↓
输出：3D gaze unit vector
```

### 当前参数量

- **GazeNet 总参数量：390,147**

### 这个模型的定位

- 作为早期基线模型
- 验证训练、推理和几何链路能否跑通
- 缺点是信息量偏少，泛化能力有限

---

## 5.2 V2：GazeNetV2（当前主模型）

### 结构图

```text
左眼图像 (3, 128, 128) ─┐
                         ├─ 共享 CNN Backbone ─> 左眼特征 256 维
右眼图像 (3, 128, 128) ─┘
                         └─ 共享 CNN Backbone ─> 右眼特征 256 维

head_pose = (yaw, pitch, roll) -> 3 维

拼接：
左眼 256 + 右眼 256 + head_pose 3
  ↓
共 515 维融合特征
  ↓
FC(515→128) + ReLU + Dropout(0.3)
  ↓
FC(128→3)
  ↓
L2 Normalize
  ↓
输出：3D gaze unit vector
```

### 共享 backbone 的卷积层结构

```text
Conv(3→32) + BN + ReLU + MaxPool
Conv(32→64) + BN + ReLU + MaxPool
Conv(64→128) + BN + ReLU + MaxPool
Conv(128→256) + BN + ReLU + MaxPool
AdaptiveAvgPool2d(1)
```

### 当前参数量

- **GazeNetV2 总参数量：455,811**

### 说明

这个参数量不大，说明当前模型是一个**轻量网络**，这和你的实时系统目标是一致的。

## 6. 当前模型每一部分为什么要这样设计？

## 6.1 为什么是 4 层卷积？

### 目的

- 提取从低级纹理到高级语义的眼部视觉特征
- 控制模型复杂度
- 保持实时性

### 你可以这样回答

> 4 层卷积已经足以把眼部图像从局部边缘、眼睑纹理逐步抽象到更稳定的视线相关特征，同时参数量仍然可控。对于当前数据规模和 CPU 实时部署目标，这是一个更稳妥的平衡点。

---

## 6.2 为什么左右眼共用同一个 CNN backbone？

### 原因

- 左右眼本质上是同类视觉结构
- 共用权重能减少参数量
- 可以降低过拟合风险
- 工程上更轻量

### 你可以这样回答

> 左右眼虽然位置不同，但视觉结构相似，所以我让它们共享同一套特征提取器。这样可以减少参数，提高样本利用效率，也更符合轻量化设计目标。

---

## 6.3 为什么要融合 head pose？

### 原因

- 单纯从眼部图像看，不同头姿下可能出现相似外观
- head pose 能补充空间信息
- 对屏幕映射精度影响很大

### 实验支持

你的消融实验显示：

- 无 pose：约 **501.9 px**
- 完整 pose：约 **365.0 px**
- 下降约 **27.3%**

### 结论

head pose 不是“锦上添花”，而是当前系统里非常关键的增益因素。

---

## 6.4 为什么要在融合层加 Dropout？

### 原因

- 你当前数据规模还不算特别大
- 融合层是高维特征到低维输出的关键位置
- Dropout 可以缓解过拟合

当前配置：

- `dropout = 0.3`

---

## 6.5 为什么最后做 L2 归一化？

### 原因

- 你要预测的是“方向”，不是任意三维向量
- 方向向量只关心朝向，不关心长度

### 好处

- 输出更符合物理意义
- 配合角度损失更自然
- 避免模型输出不稳定尺度

---

## 7. 当前模型用什么损失函数？为什么这样选？

当前项目使用的是：

- **角度损失 `angular_loss`**

代码逻辑是：

```text
loss = mean( arccos( clamp( pred · target, -1+eps, 1-eps ) ) )
```

也就是直接计算：

- 预测视线向量
- 真实视线向量
- 它们之间的夹角

### 为什么不用 MSE？

因为你预测的是方向向量，最自然的误差定义就是“方向偏了多少角度”，而不是三个坐标分量差了多少。

### 你可以这样答

> 由于我的输出是单位视线方向向量，所以我直接优化预测方向和真实方向之间的夹角，这比用普通 MSE 更符合问题本身。

## 10. 当前推理时模型怎么工作？

来自 `src/tracker/pipeline.py`，当前主流程是：

```text
1. 摄像头读帧
2. 人脸关键点检测
3. 头姿估计
4. 裁剪左右眼
5. 构造 left_eye / right_eye / head_pose
6. 调用 GazeNetV2 输出 3D gaze vector
7. 用 rotation_matrix + translation_vec 把视线方向变到相机坐标系
8. 和屏幕平面求交
9. 映射到屏幕像素坐标
10. 时序平滑
11. 输出 gaze point
```

### 推理阶段为什么还要 ONNX？

因为训练用 PyTorch 更灵活，部署用 ONNX Runtime 更适合 CPU 和跨平台。

## 13. 当前模型的“原理”怎么用非专业语言解释？

你可以这样讲：

> 这个模型的原理可以理解成：先让网络从左右眼图像里提取“眼睛朝向的视觉线索”，再把头部姿态信息一起考虑，最后输出一个人在三维空间里大致看向哪里的方向向量。

这比直接背“卷积、池化、全连接”更适合非本领域老师。

## 15. 当前模型的局限性是什么？

这个也必须熟悉，因为答辩很可能问。

### 局限 1：模型本身不是最终误差的唯一来源

即使角度误差下降了，像素误差还会受：

- 头姿估计误差
- 屏幕参数近似误差
- 几何映射误差
- 校准误差

### 局限 2：长尾用户问题还存在

少数用户误差明显偏大，说明：

- 个体差异
- 设备差异
- 眼镜反光
- 光照变化

仍然会影响模型。

### 局限 3：当前模型创新不是“理论型颠覆创新”

这点不要回避。  
更准确的说法是：

> 当前模型创新属于面向特定应用场景的结构优化与系统整合创新。
